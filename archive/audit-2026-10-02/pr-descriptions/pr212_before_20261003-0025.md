TITLE: Harden the deployment: loopback datastores, opt-in admin tools, bounded logs, pinned images, post-deploy prune

## Do not merge during a demo or a burst of work

**Merging this restarts the `postgres`, `redis` and `qdrant` containers once on the shared EC2** (a few seconds; the data volumes persist). The deploy recreates them because their published-port configuration changes, and the API and worker are recreated by the deploy anyway. In-flight runs recover through the existing retry path. Pick a quiet window. This is a **draft** so it cannot be merged by accident; mark it ready when the window is chosen.

## Why

Found during the 2026-10-02 audit of the shared host (full write-up in `docs/audit_2026-10-02.md` on #211, findings O-3 to O-5):

- `BIND_IP=0.0.0.0` on the host publishes PostgreSQL, Redis and Qdrant on **every interface**. Only the AWS security group protects them (verified closed on 2026-10-02: 5432, 6379, 6333, 6334). Qdrant has no API key. One security-group change would expose all data.
- `pgweb` and `redis-commander` are unauthenticated admin UIs on `:latest` that start on a plain `docker compose up`.
- No container log rotation, on a 19 GB disk shared with every image the host builds.
- The deploy builds on the host and never reclaims anything; about 17 GB of images and build cache had accumulated and the disk was at 77-80%.
- The Dockerfile pulls `uv:latest` and a rolling Python tag, and trusts `X-Forwarded-*` from any client.

## What changes

- `postgres`, `redis`, `qdrant` are always published on `127.0.0.1`; `BIND_IP` now applies to the API only. Services reach them over the compose network, and an SSH tunnel to localhost still works.
- `pgweb` (pinned to 0.17.0) and `redis-commander` sit behind the `tools` profile and loopback: `docker compose --profile tools up -d pgweb`.
- Every service rotates logs (10 MB x 3).
- Dockerfile pins the `uv` image (0.12.19) and `python:3.12-slim-bookworm`; `--forwarded-allow-ips=127.0.0.1`.
- `deploy.yml` prunes dangling images and build cache older than 72 h after a good deploy. A prune failure cannot fail a deploy, and the prune cannot touch volumes.
- `tests/repo/test_deployment_hardening.py` pins each of these.

## Verification

- `docker compose config` renders; default services are `postgres qdrant redis api celery-worker`; with `--profile tools` the two admin tools are added; every datastore binding is `127.0.0.1`.
- Pinned tags confirmed to exist (`docker manifest inspect`) before pinning.
- 1,794 unit tests pass; ruff, format, mypy and the secret scan are clean.

## Not verified

- Not deployed anywhere, so the one-time datastore restart and the post-deploy prune have not run on the real host.
- Not fixed here: the host has no swap and the worker was OOM-killed under a six-incident burst (audit O-8). That is a capacity decision for the team (swap, a lower `WORKER_CONCURRENCY`, or a larger instance), not something to change blind in a PR.
